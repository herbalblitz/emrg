# Companion Pairing v2 — Design and Security Gates

Status: host WSS request/redeem adapter prototype exists; Android coordinator is not wired. Pairing remains a gated prototype, not a production-ready end-to-end feature.

Date: 2026-11-19

## 1. Purpose and non-goals

Define a host-approved, one-time pairing exchange that connects the existing host-side pairing transaction primitives to Android without weakening the current trust boundaries.

This design does **not** enable remote chat, tool execution, filesystem access, or remote pairing administration. The current WSS listener remains limited to authenticated `status` and read-only `sessions.list`.

## 2. Existing implementation boundary

- QR descriptor v1 contains only `version`, `endpoint`, `fingerprint_sha256`, and `expires_at`. It is WSS-only, SAN-checked, short-lived (at most 180 seconds), and credential-free.
- Host pairing transactions already support bounded pending requests, expiry, explicit local approve/reject, cancellation, one-time redemption, and credential issuance.
- `CompanionHostService.redeem_pairing` is a host-local service operation, not a WSS endpoint.
- The WSS listener now has a dedicated one-frame unauthenticated `pairing.request` / `pairing.redeem` route. It delegates to the host v2 transaction service, applies per-peer rate limiting, and keeps approval exclusively in the host-local service. This route is separate from authenticated status/session dispatch.
- Android parses descriptor v1 and has a secure credential store and pinned-WSS primitive, but its pairing UI/coordinator is not connected to a complete host-side exchange.
- Android's self-approval affordance has been removed. The device must wait for a host-side decision.

These components must not be treated as an end-to-end pairing implementation. In particular, the current request-frame validator/adapter still does not require the design's `requested_scopes` and `client_nonce` fields, and the host transaction API does not yet validate or bind those values. The Android request builder likewise omits them. This wire-contract mismatch is a blocking integration task; do not silently widen scopes or claim replay protection from a client nonce.

## 3. Security invariants

1. **Host approval is authoritative.** Only a trusted local host UI/API can approve or reject a pending device. A remote Android client cannot approve itself.
2. **No reusable credential in QR.** QR data never contains a device credential, bearer access token, private key, or long-lived secret.
3. **Bind approval to a device key.** Android generates a fresh device key pair before requesting approval. The host's pending request and approval record bind to the public-key fingerprint, device ID, requested workspace, and exact requested scopes.
4. **Proof of possession.** Redemption proves possession of the private key corresponding to the public key shown in the host approval UI. Merely knowing a transaction identifier is insufficient.
5. **One-time and short-lived.** A transaction can be redeemed once, expires no later than 180 seconds after creation, and is consumed atomically before credential issuance.
6. **TLS identity pinning.** Android validates the WSS certificate against the fingerprint in the scanned descriptor before sending pairing messages. The host validates the endpoint against its provisioned identity.
7. **Least privilege.** The host displays and approves exact scopes. The device cannot widen scopes, choose a different workspace, or supply a host filesystem path.
8. **Fail closed.** Expiry, replay, wrong device key, wrong transaction, cancellation, rejection, malformed frames, or persistence failure must not create or retain a usable credential.
9. **No secret logging.** Pairing payloads, proofs, credentials, and private key material are excluded from logs, analytics, crash metadata, and exception text.
10. **Compatibility is explicit.** v1 descriptors remain parseable for host identity verification but cannot initiate v2 pairing. Unknown versions and fields are rejected.

## 4. Proposed v2 descriptor

The v2 QR remains a locator and transaction reference, not a credential container:

```json
{
  "version": 2,
  "endpoint": "wss://host.example:8443",
  "fingerprint_sha256": "AA:BB:...:FF",
  "expires_at": 1790000000,
  "pairing_id": "<256-bit-random-opaque-id>"
}
```

- `pairing_id` is generated by the host from a cryptographically secure random source and is not an authorization decision.
- The descriptor contains no `credential`, `token`, `secret`, `password`, private key, or access scope grant.
- The host creates the pending transaction before rendering the QR. QR generation must fail if the transaction is absent, expired, cancelled, or already consumed.
- The transaction ID must not be reused. It should be stored hashed at rest where practical and redacted from logs.
- A QR scan alone does not authorize a device. Host approval is still mandatory.

## 5. Proposed exchange

1. **Host creates transaction.** Trusted local host UI selects workspace and requested maximum scopes. Host creates a pending transaction with random ID, creation/expiry timestamps, and policy metadata; no device credential is issued.
2. **Host displays QR.** QR v2 contains WSS endpoint, TLS fingerprint, expiry, and opaque pairing ID.
3. **Android creates identity.** On scan, Android creates a fresh per-host P-256 EC key pair in Android Keystore. The private key never leaves the device. Android creates a random request nonce.
4. **Android requests approval.** Over pinned WSS, Android sends `pairing.request` containing protocol version, pairing ID, device ID, P-256 SubjectPublicKeyInfo public key, the explicit `key_algorithm: P-256` identifier, requested scopes, and nonce. The host checks descriptor/transaction expiry, transaction state, scope subset, field bounds, and replay nonce.
5. **Host presents pending request locally.** Trusted host UI displays a human-readable device label, device ID, public-key fingerprint, workspace, requested scopes, and expiry. It does not expose a secret that can approve the request remotely.
6. **Host approves or rejects.** Local host action atomically binds approval to that exact device ID and public-key fingerprint. Rejection/cancellation consumes or removes the pending transaction. Approval cannot be changed after redemption.
7. **Device proves key possession.** Host returns a fresh challenge tied to pairing ID, transaction expiry, device ID, public-key fingerprint, and host identity. Android signs the canonical challenge using `SHA256withECDSA` with its Keystore private key.
8. **Android redeems once.** Android sends `pairing.redeem` with pairing ID, device ID, public key fingerprint, challenge ID, and signature. Host verifies the signature and all transaction bindings, atomically consumes the approved transaction, then issues a credential bound to device ID, public key, workspace, and approved scopes.
9. **Android persists safely.** Credential delivery is bound to the same TLS-pinned connection and device key. Android validates the response binding and persists the credential in the encrypted credential store. Persistence failure triggers best-effort host revocation and leaves the client unpaired.
10. **Authenticated reconnect.** Future WSS authentication proves possession of the registered device key in addition to the issued credential, or uses a formally documented credential rotation scheme. A copied credential alone should not be sufficient if the protocol adopts key-bound authentication.

## 6. Wire protocol requirements

All messages use strict JSON parsing with duplicate-key rejection, bounded frame sizes, exact allowed-field sets, and safe generic errors.

### Client: pairing.request

Required fields:
- `type = "pairing.request"`
- `protocol = "2.0"`
- `pairing_id`
- `device_id`
- `public_key` (bounded encoded public key; algorithm explicitly named)
- `key_algorithm = P-256` (the only supported v2 key algorithm)
- `requested_scopes` (unique, bounded allowlist)
- `client_nonce` (at least 128 bits of cryptographic randomness)

### Host: pairing.pending

Returns a non-secret request reference and a host-generated challenge. It must not imply approval or return a credential.

### Client: pairing.redeem

Required fields:
- `type = "pairing.redeem"`
- `protocol = "2.0"`
- `pairing_id`
- `device_id`
- `challenge_id`
- `signature`

The signed canonical challenge must cover protocol version, pairing ID, device ID, public-key fingerprint, host identity/fingerprint, transaction expiry, workspace ID, and exact approved scopes. Canonical encoding must be specified and tested before implementation.

### Host: pairing.credential_issued

Credential response must be delivered only after atomic transaction consumption and successful proof verification. It must include enough non-secret binding metadata for Android to verify that the credential is for the expected device, host, workspace, and scopes. The credential itself must never be written to logs or QR data.

## 7. State machine

```text
CREATED
  -> AWAITING_DEVICE_REQUEST
  -> AWAITING_LOCAL_HOST_DECISION
       -> REJECTED (terminal)
       -> CANCELLED (terminal)
       -> APPROVED_FOR_DEVICE_KEY
            -> AWAITING_DEVICE_PROOF
                 -> REDEEMED (terminal; one credential issuance)
                 -> EXPIRED (terminal)
                 -> CANCELLED (terminal)
                 -> FAILED (terminal; no credential)
```

Every transition is host-authoritative and atomic. Duplicate requests, approvals, or redemption attempts must be idempotently rejected without issuing a second credential.

## 8. Required test matrix

### Descriptor and parser
- v1 remains accepted only for its existing host-verification use; v1 cannot initiate pairing.
- v2 valid descriptor, expiry boundary, maximum TTL, malformed JSON, duplicate fields, unknown fields, unsupported version.
- Reject embedded credentials, tokens, passwords, private keys, and any unexpected secret-like fields.
- Reject malformed/oversized pairing IDs and non-WSS endpoints.
- Confirm fingerprint and expiry are bound to the transaction and TLS identity.

### Host transaction and listener
- Request for unknown, expired, cancelled, rejected, or consumed pairing ID.
- Host approval from remote client is impossible.
- Approval binds exact device ID, key fingerprint, workspace, and scopes.
- Scope escalation, workspace substitution, wrong key, invalid signature, wrong challenge, replayed nonce, and duplicate redemption.
- Race two concurrent redemption requests; exactly one can succeed.
- Host disable/shutdown invalidates pending transactions and closes sockets.
- Pending queue and rate limits remain bounded; no secrets appear in logs.

### Android
- Generate and retain per-host private key in Keystore; private key never serializes.
- Reject WSS certificate mismatch before sending pairing data.
- Reject host challenge with mismatched transaction/device/host/expiry/scopes.
- Credential response binding mismatch is rejected.
- Keystore persistence failure leaves state unpaired and initiates revocation.
- App restart, process death, cancellation, expiry, and retry do not create duplicate credentials.

### Cross-platform end-to-end
- Android ↔ Windows host and Android ↔ supported desktop host.
- Approval, rejection, timeout, cancellation, host shutdown, replay, wrong device, and credential revocation.
- Verify that existing v1 QR parsing and authenticated status/session operations do not regress.

## Android device-key compatibility gate (2026-11-19)

The protocol decision is P-256 ECDSA to align with Android Keystore's documented EC key-generation and SHA-256 ECDSA signing APIs. The host transaction core and strict frame validator now accept only P-256 SPKI public keys and ECDSA/SHA-256 proofs; the request frame carries the explicit `key_algorithm: P-256` marker.

This removes the unsupported assumption that Ed25519 is available in Android Keystore across API 26+ devices. It does not prove every Android device has a usable secure implementation. An Android Keystore P-256 key-manager implementation now exists, with a transport-neutral client helper and JVM protocol tests. Pairing v2 remains disabled until physical-device tests establish non-exportable key generation, persistence, and signing on supported API levels. Do not silently fall back to software-generated/exportable keys.

See [ANDROID_COMPANION_DEVICE_KEY_COMPATIBILITY_AUDIT.md](ANDROID_COMPANION_DEVICE_KEY_COMPATIBILITY_AUDIT.md) for evidence, options, and required validation.

## 9. Implementation gates and sequencing

1. Select and document public-key algorithm, canonical challenge encoding, signature algorithm, and credential key-binding format.
2. Implement host transaction schema and atomic transitions with unit tests first.
3. Add strict protocol validators and WSS pre-auth pairing route with rate limits; do not weaken existing authenticated-operation dispatch.
4. Add trusted local host pending-request UI and explicit approve/reject controls.
5. Add QR v2 creation and Android parser; retain v1 compatibility without enabling v1 redemption.
6. Add Android Keystore device identity, signed challenge, redemption coordinator, and credential persistence.
7. Add Windows/Android cross-platform integration tests and CI coverage.
8. Only then enable pairing end-to-end behind an explicit opt-in feature flag.

Until all gates pass, keep live pairing and Android chat transport disconnected. Do not dispatch `CredentialIssued` from local UI state, fabricate host approval, or add a credential to the QR descriptor.


## Prototype implementation update (2026-11-19)

The host-side v2 transaction core now has an isolated implementation in `emrg/server/companion_pairing_v2.py`:

- Uses P-256 ECDSA device keys. The request carries a canonical Base64URL-encoded X.509 SubjectPublicKeyInfo public key and an explicit `key_algorithm: P-256`; redemption carries a canonical Base64URL-encoded ASN.1 DER ECDSA signature over SHA-256.
- Host creates a 256-bit opaque transaction ID; a device submits one public key and device ID for that transaction.
- The host-local pending view exposes the device ID and SHA-256 public-key fingerprint for the approval decision; it does not expose private key material.
- The signed canonical JSON challenge binds protocol version, transaction ID, challenge ID/nonce, device ID, public-key fingerprint, configured host identity, workspace, exact scopes, and transaction expiry.
- Redemption verifies the P-256 ECDSA/SHA-256 proof and exact device/challenge binding, then consumes the transaction before issuing the credential.
- Host service exposes local begin/pending/approve/reject operations and adapter-facing request/redeem methods. Disabling the service cancels v2 pending transactions.

This is a transport-independent core only. The current WSS listener does not call these methods; QR v2 generation, TLS-certificate fingerprint plumbing, rate limiting at the new request endpoint, Android Keystore signing, and Windows/Android end-to-end integration remain gates. Do not describe v2 pairing as live until those pieces and CI are complete.

### Android descriptor/parser progress (2026-11-19)

The Android companion now has a versioned descriptor parser in
`android/app/src/main/java/ai/emrg/companion/PairingDescriptorParser.kt`:

- v1 remains compatible and produces no pairing transaction ID.
- v2 requires a canonical, unpadded Base64URL `pairing_id` encoding exactly 32 bytes.
- Both versions require a secure WSS endpoint, a SHA-256 certificate fingerprint,
  and an expiry no more than 180 seconds in the future.
- Duplicate top-level JSON keys are rejected before `JSONObject` parsing, including
  names that become duplicates only after JSON escape decoding.
- Credential-bearing field names are rejected case-insensitively; unknown fields
  and incorrect endpoint/fingerprint JSON types fail closed.
- The parser requires `pairing_id` to be a JSON string; it does not coerce other
  JSON types into strings.

The host-side strict v2 frame validator also rejects duplicate keys after JSON
escape decoding. These parser/validator changes do not add a WSS pairing route,
generate a device key, approve a request, or issue a credential. The transport and
host-approval gates above remain unchanged.

### Android device-key implementation gate clarification (2026-11-19)

The host prototype now fixes proof-of-possession to P-256 ECDSA with SHA-256.
The Android implementation must not silently substitute another signature
algorithm or serialize an unencrypted private key when a device/provider cannot
create or use the required key.

Before implementing the Android key manager, add a compatibility test matrix for
the project's supported Android API levels and representative Keystore providers.
The test must cover key generation, public-key encoding, signing the exact
canonical challenge bytes, signature verification by the host, persistence across
process restart, and key invalidation. If the required operation is unavailable,
pairing must fail closed with a user-safe unsupported-device result until a
protocol-approved alternative is designed and documented. This gate does not
use the explicit P-256 ECDSA wire contract.


### Android credential-envelope hardening (2026-11-19)

The Android encrypted credential store now validates its persisted AES-GCM envelope
before invoking the Keystore cipher:

- The persisted representation remains the existing `standard-Base64(IV).standard-Base64(ciphertext)`
  format, preserving compatibility with credentials written by the previous
  `Base64.NO_WRAP` implementation.
- The IV must decode to exactly 12 bytes; ciphertext must contain at least the
  16-byte GCM authentication tag.
- Both Base64 components must be canonical padded standard Base64. Whitespace,
  alternate padding, extra separators, truncated values, and malformed dimensions
  fail closed before decryption.
- The codec is platform-independent so malformed-envelope behavior can be covered
  by JVM unit tests without invoking Android Keystore.

This hardening does not alter credential encryption, key aliases, AAD binding,
credential contents, or the host protocol. Android CI must pass before treating
the change as validated; device/Keystore integration remains a separate test gate.


### Android credential size and encryption-parameter hardening (2026-11-19)

The Android credential store and pairing coordinator now enforce the host credential
registry's 512-byte UTF-8 credential limit before persistence. Blank, oversized, and
multi-byte values exceeding the byte limit are rejected without writing a credential.
The AES-256-GCM Android Keystore key-generation specification also explicitly requires
randomized encryption. This documents and reinforces the existing envelope/AAD
contract; it does not change the host credential format or pairing protocol.

JVM tests cover the 512-byte boundary, blank values, oversized ASCII values, and
multi-byte UTF-8 values. Android CI must pass for the complete source/test commit.
These JVM tests do not substitute for physical-device Android Keystore validation.


### Credential text encoding boundary (2026-11-19)

- Android credential validation now uses a reporting UTF-8 encoder rather than replacement-based string conversion. Malformed UTF-16 input (including unpaired surrogates) is rejected before the 512-byte bound is evaluated or persistence is attempted.
- Regression coverage includes an unpaired high surrogate. This prevents Java/Kotlin replacement encoding from silently changing credential bytes before storage.
- Android CI #207 failed during Gradle dependency resolution because Maven Central returned HTTP 429 for multiple artifacts; APK assembly did not reach Kotlin compilation. Android CI #210 passed APK assembly, JVM unit tests, lint, and artifact upload for the 512-byte credential-boundary changes. Android CI #213 was queued for the malformed-Unicode and strict-decode changes; its final result must be checked independently.


- The encrypted credential store also decodes decrypted bytes with a reporting UTF-8 decoder and re-applies the credential validity/512-byte checks on read. Malformed or out-of-contract stored plaintext now fails closed instead of being silently replacement-decoded.

### Android P-256 device-key and Pairing v2 client foundation (2026-11-19)

The Android source now contains a non-exportable P-256 Android Keystore key-manager
foundation in `AndroidKeystoreDeviceKeyManager.kt`. It creates/loads a per-host
EC key alias, requires the private-key handle to be non-exportable, exports only
the DER SubjectPublicKeyInfo public key, signs with `SHA256withECDSA`, and
supports explicit alias deletion. The implementation has no software-key fallback.

The transport-neutral `PairingV2Client.kt` builds the strict
`pairing.request` frame with `key_algorithm: P-256`, validates canonical
Base64URL transaction identifiers and the host challenge's protocol, transaction,
device, public-key digest, expiry, nonce, workspace, and allowed scopes, then signs
the exact challenge UTF-8 bytes and builds `pairing.redeem`. It does not open a
socket, approve a request, or persist a credential.

The wire encoding is:
- Public key: canonical unpadded Base64URL of DER X.509 SubjectPublicKeyInfo
  for a P-256 EC key (typically 91 DER bytes / 122 Base64URL characters).
- Proof: canonical unpadded Base64URL of the ASN.1 DER ECDSA signature over
  SHA-256 of the exact host challenge bytes.

A small `CompanionDeviceKeyManager` interface permits JVM protocol tests to
supply a test signer without pretending that a software test key is Android
Keystore-backed. The Android implementation remains the production signer.

The Android v2 helper is not yet wired to `SecurePairingCoordinator` or the
pinned WebSocket. The host WSS adapter prototype exists, but its request frame
is not yet fully aligned with the design contract (`requested_scopes` and
`client_nonce` are missing end-to-end). Host approval remains a separate
trusted-local action. Live Pairing v2 must remain unavailable until wire-contract
alignment, coordinator and transport integration, physical-device Keystore tests
(including API 26), process-restart persistence, and end-to-end Python/Android
signature interoperability are verified. JVM tests do not prove secure-hardware
availability or actual Android Keystore behavior.


### Pairing v2 client hardening follow-up (2026-11-19)

- Android now binds a redeem attempt to the exact pairing ID used by the most recent successfully constructed request frame. A challenge for a different transaction is rejected before signing.
- Starting a new request clears the prior in-memory transaction/key binding first, so a failed new request cannot leave the previous transaction eligible for redemption.
- Regression coverage rejects redeeming a different pairing transaction.
- These are protocol-helper safeguards only. They do not add a WSS route or enable live pairing; host-side approval, transport integration, credential response binding, and physical-device validation remain release gates.


### Host WSS adapter implementation update (2026-11-19)

The listener prototype in `emrg/server/companion_wss_listener.py` now routes
only the initial `pairing.request` and `pairing.redeem` frames to the v2 host
service before normal authenticated-session dispatch. The route is one-frame
and unauthenticated by design, returns a generic `pairing_unavailable` error
for transaction/proof/approval failures, and never exposes remote approve or
reject operations. The per-peer limiter is bounded to 1,024 peers and 10
attempts per 60-second window.

Tests currently exercise request/redeem, local-only approval, redemption before
approval, replay rejection, generic error behavior, and per-peer rate limiting.
This is still only a transport adapter prototype: the wire request does not yet
carry or enforce `requested_scopes` and `client_nonce`, and Android does not
yet connect its coordinator to this route. Those are explicit blockers, not
implicitly satisfied requirements.
